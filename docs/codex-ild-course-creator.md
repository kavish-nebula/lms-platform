# Codex-assisted ILD course creation

The authoring route uses Codex during course creation. It does not run an LLM job from the LMS server. The creator opens a saved brief, creates a short-lived course-scoped connection, adds the endpoint and bearer-token environment variable to local Codex MCP configuration, then asks Codex to use the `course-creation` skill. The coordinator reads the saved SME context, runs the specialist workflows in the same conversation, assembles a complete course and saves an append-only editable revision through the LMS MCP tools. The LMS validates the imported structure and source/objective references.

## Six coordinated skills

The former `ild-course-creator` skill is retired. Its replacement lives under `.agents/skills/`:

| Skill | Owns | Standalone request |
| --- | --- | --- |
| `learner-profiling` | Audience analysis or a separate advisory individual-profile report | Analyze an audience or recommend learner support |
| `course-creation` | Plan, ID/source registry, objective evidence, assembly, reflection and final draft save | Create, revise, assemble or save a complete course |
| `lesson-generation` | Hook, slides/narration, examples, guided practice and scenarios | Generate or revise teaching content |
| `quiz-generation` | Two formative midpoint items per video, module-end quizzes and one comprehensive final Mastery Gate | Generate or revise assessments |
| `mini-project-generation` | One course-end applied project and observable rubric | Generate or revise the capstone |
| `course-quality-review` | Evidence-based findings and readiness recommendation | Review an assembled course |

Start a full build with `Use $course-creation to create a course from the saved SME brief.` The coordinator runs audience analysis, planning, lesson generation, quiz generation, mini-project generation, assembly/reflection and quality review in order. It allows at most two automatic correction rounds, then returns unresolved blockers without saving an incomplete draft. A specialist-only request ends with its fragment/report; saving continues through the coordinator only when requested.

New-course lesson authoring requires 3-4 modules and 3-4 concept topic videos per module, chosen according to the subject and complexity. Every video has exactly two midpoint questions and a playback budget no longer than seven minutes, including narration and visual pauses/transitions; learner-controlled quiz time is counted separately. After its concepts, every module includes worked examples, guided practice and a scenario lab. Videos should use plain language, concrete examples, purposeful visual progression and accessible alternatives. These are skill-level authoring/review requirements: the existing schema, MCP tools and player are unchanged, and existing approved courses are not automatically restructured. Script durations remain estimates until actual media is checked.

The updated assessment authoring design adds one quiz after each module's Scenario Lab and one course-end final assessment covering every taught topic/objective. Some final questions must have multiple correct choices and visibly say **Select all correct answers**. Options must have similar length, detail and grammatical structure so a longer choice does not reveal the correct answer. The backward-compatible schema now supports optional module `moduleQuiz` objects and multiple-answer questions. The player displays module quizzes after Scenario Lab using the existing `gate` stage. Single-answer questions retain numeric `correct`; multiple-answer questions use `selectionType: "multiple"` and `correctIndices` with at least two correct choices and one distractor. Module quizzes have `title`, `instructions`, `questions` and optional `passPercent`; an omitted module threshold inherits the final assessment percentage. Existing saved courses without module quizzes retain their original flow. No existing courses are automatically edited or republished.

Practical-project authoring requires exactly one integrated project after all modules/quizzes, covering every taught concept and objective with clear numbered instructions, deliverables and grading criteria. All required work must be performed in a sandbox inside the course, including building/editing, execution or simulation, testing, inspecting results and submitting evidence; no outside environment is required. The project handoff carries a coverage map and sandbox requirements in dependencies. Authored projects now support optional `miniProject.sandbox` configuration for an in-course data-workflow simulator. Learners edit fields and ordered operations, run sample data, test multiple cases, save drafts and submit for server-computed rubric grades. Configuration includes instructions, fields, inputs, starterSteps, tests and weighted criteria mapped one-to-one to rubric indices, with objective/source/video coverage. A missing project passPercent requires every criterion to pass. Work is scoped to enrolled learner and release revision; edits invalidate the current report, while immutable submissions remain. This bounded interpreter does not execute arbitrary code or external integrations; unsupported runtimes remain blockers. Historical packages without sandbox configuration retain their previous flow.

The [shared workflow contract](../.agents/skills/course-creation/references/workflow-contract.md) is the single handoff reference. Handoffs retain course/brief scope, base package version, stable target/objective/source IDs, owned content, assumptions, unresolved questions and dependencies. Intermediate lesson fragments may omit quizzes until the quiz handoff arrives; only a complete existing `schemaVersion: 1` package is sent to `save_course_draft`. Handoff envelopes are never extra persisted package fields. Revisions preserve unrelated content and recheck affected dependencies.

Audience profiling uses the creator's SME context. Individual profiling is a separate advisory mode using explicitly supplied, authorized learner context; it does not read learner data through the course-scoped MCP, write profiles/progress, change assessment difficulty or modify the master course. A quality recommendation is not human approval, factual certification or publication.

This is a skills-and-handoffs refactor: there are no new MCP tools, staged database checkpoints, background agents or app-driven execution. Existing profiling, planner, generation, review and publication services keep their current behavior. Existing MCP configuration and grants continue to use the server name and endpoint below.

The MCP server is `POST /api/mcp/ild-course-creator` (Streamable HTTP). It exposes `get_course_context`, `get_course_draft`, and `save_course_draft`. A generated token is scoped to one course, stored only as a SHA-256 hash, expires after eight hours, and is revoked when another token is issued or when the creator revokes it. The token is returned once. The UI provides a TOML server entry for `%USERPROFILE%\.codex\config.toml` using `bearer_token_env_var = ""`, plus a PowerShell `setx` command to store the token outside that file. Restart Codex after configuration. Do not paste the token into source control, issue trackers or shared documents. Each MCP tool call derives ownership and course scope from the token, not tool arguments.

The current app's `getSessionUser` still supplies a shared local demo identity. Therefore the per-course token prevents accidental cross-course tool calls, but does not provide production user identity or tenant isolation. Replace the demo session with a real identity provider before enabling this connection for external production teams.

## Validation and routing exercises

Run `python <skill-creator>/scripts/quick_validate.py .agents/skills/<name>` for each of the six folders (requires PyYAML). Run the isolated package exercise from `apps/web` with `node tests/backend/run.mjs course-skills`. It assembles teaching, quiz and project fragments using the existing validator and an in-memory database; it never connects to a live course. It checks exact objective text, midpoint placement and first-half objective scope, source links, unique IDs, final coverage, focused-edit preservation and rejection of stale brief/package versions. Source truth and semantic teaching quality still require review.

The following instruction walkthroughs use that fixture's fictional handoff conventions. These are manual routing exercises against the skill instructions, not an automated model-routing benchmark or a live MCP run:

| Request / supplied context | Entry and reviewed outcome |
| --- | --- |
| “Create a complete course from this saved brief.” Two objectives, two source blocks and a creator pass rule are supplied. | `course-creation`: audience analysis, plan, teaching, quizzes, project, assembly/reflection, review, then current-version checks. Only the assembled package is eligible for saving. |
| “Rewrite narration on M1SL2 only.” The current package is supplied. | `lesson-generation`: return a slide-targeted teaching patch; flag its checkpoint dependency. Preserve the other module, assessments and course end; no save on a standalone request. The synthetic exercise verifies preservation when the coordinator applies this patch. |
| “Write the checkpoint for M1V1.” The first slide teaches named owners; the second introduces a separate convention. | `quiz-generation`: exactly two questions supported by the first slide after M1SL1, with answer keys and feedback. Do not test the later convention or replace the final gate. |
| “Design the course-end project.” Both taught objectives and sources are supplied. | `mini-project-generation`: one handoff combining a named owner and a checkable deliverable, with an observable two-criterion rubric; return only the project fragment. |

The `authored-assessment` suite additionally exercises multiple-answer schema rejection, exact-set server scoring, module scope, stale releases, learner key privacy, exports, signal verification and persisted gate progress. The existing `authored-course`, `authored-publication`, `enrollment-start` and `profiling` backend suites cover the unchanged server and learner boundaries. Instruction walkthroughs do not establish that every future model execution will follow the skills; assess generated content and tool behavior on each real authoring run.

## Course package shape

`schemaVersion` is `1`. The package contains `title`, `subject`, `durationMinutes`, `briefRevision`, `sources`, `objectiveEvidence`, `modules`, and `courseEnd`.

- Sources use unique stable IDs. SME sources use the `S1`, `S2`, … IDs returned by `get_course_context`. Research sources use `kind: "research"`, a title, publisher/reference and URL (`R1`, `R2`, … are provided for the saved reference links).
- `objectiveEvidence` includes every supplied `O1`, `O2`, … objective with its exact SME wording and relevant source IDs. Every module also has source IDs, so reviewers can follow objective and module provenance as well as item-level citations.
- Every module has a stable `id`, title, duration, objective IDs, a `problemHook`, a `conceptExplainer` with one or more videos, `workedExamples`, `guidedPractice`, and `scenarioLab`. New authored modules also include `moduleQuiz` (`title`, `instructions`, `questions`, optional `passPercent`); it remains optional in the schema to preserve historical courses. Every supplied module quiz must assess each objective assigned to its module and cannot reference another module's objectives.
- Each video has a flexible number of slides. Each slide has a stable ID, editable title/body, narration, optional planned narration seconds, objective IDs and source IDs.
- Each video has exactly two `midpointQuiz` questions and an `afterSlideId` pointing to the midpoint slide. Formative questions are not graded course mastery.
- Questions use either numeric `correct` with optional `selectionType: "single"`, or `selectionType: "multiple"` with `correctIndices`. Multiple-answer keys require unique valid indices, at least two correct choices and at least one distractor. The player supplies visible selection instructions. Module/final submissions go to the existing assessment endpoint with the exact `revisionId`, optional `moduleId` (omitted for the final), and `responses` mapping question IDs to option-index strings or arrays of strings. Correctness is computed from the published package; duplicate/unknown choices, response-type mismatches, cross-scope questions and stale revisions are rejected. Missing or extra valid selections receive no credit.
- `courseEnd` contains one `miniProject`, one `masteryGate` with a creator-set integer `passPercent` and objective-linked questions, and `reflection` prompts—in that order.
- Keep IDs unique across the course. Each instructional item must cite one or more known SME or research sources. The save validator checks references and coverage; it does not fetch URLs or prove factual accuracy.

## Human review and release

Every edit is a new saved revision. Final review records apply to one exact revision; an edit or brief change makes that revision historical/outdated. After approval, the creator can publish the exact latest revision and its latest approval to the learner catalog. Publication preserves the released version when authoring changes later. Released packages now use the same catalog, course journey, enrollment, module player, narrated video/reader, practice and finale components as Build Your First AI Agent. Enrollment and module progress persist through existing services; project text, finale state and demo credentials retain the reference experience's local storage. Final grading uses the exact server-side release, and narration audio is limited to that release's slide IDs. Automated checks assist the reviewer and do not establish SME approval, factual accuracy, accessibility conformance or instructional quality.

## Later phase

Direct LMS generation requires a durable background job service and provider credentials on the server. It must use the same package schema, validation, revision history and final human sign-off. A Codex MCP connection must not be treated as the production LMS generation worker.
