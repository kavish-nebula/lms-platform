# Adaptive teaching system design

The practical sandbox separates content, learner state and authoritative grading. miniProject.sandbox declares bounded data-workflow fields/steps/input cases and criterion predicates. Package validation checks rubric/objective/video coverage and valid test references; instructional semantics remain human reviewed. The existing session scopes the project-sandbox API to an enrollment and published revision. Save/Submit lock release/enrollment and check optimistic versions, preventing stale tab/release writes. Run can execute locally; Test and Submit use published server predicates. Submission artifacts and reports are append-only. Migration 0019 adds release-scoped drafts/submissions; earlier revisions and reference-course workflows remain intact. Supported tasks are structured artifact/data-flow simulations, not arbitrary code execution or live tools.

Authored module quizzes and multiple-answer questions now use the existing delivery and grading boundaries. Optional moduleQuiz fields preserve old JSON packages; strict single/multiple question variants reject ambiguous keys. The released assessment endpoint accepts optional moduleId and scalar/array responses, rejects stale releases and cross-scope or invalid selections, and uses exact-set grading. Keys for module and final quizzes remain server-side; explanatory feedback is withheld on failed attempts. Video midpoint checks remain formative and can also use multiple selections. Telemetry verification calls the shared authored grader directly on the server. Existing progress and publication approval records are retained.

Repository authoring skills now separate learner profiling (audience or advisory individual mode), course coordination, lesson generation, quiz generation, mini-project generation and course quality review. The course coordinator merges owned fragments under the existing course/brief/package-version checks and alone saves complete drafts through the current MCP. Review findings remain advisory and cannot grant human approval. The individual mode accepts explicitly supplied authorized context and performs no learner/profile/master-content writes. This is an authoring-time instruction split, not a replacement for runtime profiling, adaptive workers, course generation services or publishing; no tools or data migrations are added.

Migration 0018 adds authored release pointers to immutable package and approval records. Publication locks the owner-scoped course, rejecting stale briefs, older revisions and superseded approvals. Learner data access includes released packages through a pure adapter to the same learner delivery types as the reference AI Agent course. Enrollment/planning and module progress use existing services; finale state and demo credentials retain the reference course's local persistence. Course-scoped preview keys prevent collisions and cross-course imports while preserving legacy AI Agent keys. Released narration is served only for the pinned revision. Final grading takes keys and thresholds from the released server package and rejects stale revisions; final assessment never adapts. Reviewed source teaching is not automatically rewritten. Demo-session identity remains a deployment limitation.

Stage 4 module production is a separate master-content authoring pilot, independent of adaptive learner delivery. It generates slides/scripts only after an explicit current module approval, snapshots source evidence and keeps edits and script decisions versioned. Source approval changes invalidate current authoring eligibility. Audio, learner publication, interactive assessment runtime and course-wide release gates are deliberately deferred.

Stage 3 SME QC records explicit module decisions against an exact creator blueprint run. Events are append-only; current input revision/prompt and all seven SME checks must match for approval. Updated source input invalidates current approval status without deleting history. Rejection/revision feedback is saved for the author; regeneration and publishing are separate actions. Shared demo identity remains a production limitation.

The local Content Creator Studio adds a separate authoring flow at `/content`: session-owned course briefs and versioned Stage 2 AI blueprints. Generation uses a frozen input snapshot, bounded LLM repair, structural validation and attempt leases in the existing database. Execution currently uses Next.js `after()`; an independent authoring worker remains a production requirement. It does not enqueue adaptive jobs or alter published course content. Asset generation, final release sign-off, pilot release and versioned publishing remain future stages. See [creator contracts and roadmap](content-creator.md).

The current implementation is a Next.js LMS with PGlite locally and an optional PostgreSQL connection. The full-platform FastAPI roadmap in [backend-plan.md](../backend-plan.md) is separate from the implemented [adaptive teaching pilot](adaptive-teaching.md).

For the pilot, the browser connects to Next.js for identity, enrollment, scoring, progress and SSE delivery. Next.js owns persistent generation jobs, immutable slide revisions and versioned performance summaries. A Python worker claims jobs through authenticated internal APIs, invokes the private FastAPI teaching editor, and returns validated output for narration and publication through the existing speech integrations. It renews job leases while generation and narration run.

Enrollment creates Module 1 jobs from a snapshot of profile and course answers. Explicit explanation requests and wrong in-lesson checks create high-priority current-slide jobs. Completion of Module 1 persists verified evidence and an updated plan before queuing Module 2. Late evidence creates a new summary/content generation; it does not rewrite completed progress or change the final assessment. Stage identifiers and authored learning objectives are stable.

The pilot uses the existing shared demo identity and local audio files. It is bound to loopback through the launcher. Multi-user authentication, object storage, provider-quality evaluation and production operations remain deployment work. The detailed contracts, failure handling, setup and checks are documented in [adaptive-teaching.md](adaptive-teaching.md).
Automatic handoff: server-graded Module 1 answers refresh Module 2 jobs before Module 1 completion; completion remains a final flush/refresh point. Playback-only telemetry does not invalidate generated teaching. A separate background worker lane generates these revisions, and opening a slide promotes its preparation ahead of older background jobs. Matching text/audio pairs are adopted only before playback or on a later slide visit.

Creator narration uses separate owner-scoped audio jobs and local media. Jobs snapshot exact script review and voice settings; the existing Kokoro child process synthesizes clips, with token-guarded progress and explicit retries. Approval changes invalidate current status without deleting media. This authoring lane does not publish to learners. A durable queue and object store remain production work.

Stage 4 long-form jobs bind exact blueprint/module approval, plan revision, plan review and video unit. Five videos of 7–9 slides each require measured narration 300–420 seconds per slide. Word count is only a pre-audio review floor. Owner-scoped creator activity previews have no learner-grade effects. Format activation does not rewrite SME input; publishing and production authentication remain separate work.

Course delivery structure v1: creator courses can opt into a separately persisted six-stage module sequence (Problem Hook → Concept Explainer → Worked Example → Guided Practice → Scenario Lab → Quiz). Migration 0015 defaults existing courses to legacy. Owner-scoped delivery-structure PATCH uses an expected-value conflict check; it leaves SME revisions and reviewed media untouched. Mastery Gate, Reflection and Spaced Review occur only after the final module, with no mini-project. Creator brief, blueprint, review and long-form views show this policy. Existing frozen blueprints remain source records; a new prompt-v3 blueprint freezes the policy and existing module IDs/order and requires fresh review. Approved prompt-v2 source/media remain supported, never rewritten or implicitly reapproved. Course-end assets require separate authoring and review; this setting does not publish content or change learner progress.

Long-form midpoint checkpoints: newly generated plans require exactly two source-linked formative questions after the midpoint slide of each video (after slide 4 for an eight-slide deck). Questions cover only first-half source/objective links. The reviewed plan freezes the checkpoint in the video package; changes require plan revision and renewed review. Creator playback pauses at that boundary, retains prior correct answers during hint/retry, then resumes the next matching clip after both questions are correct and the user chooses Continue video. Quiz time is activity time, excluded from the 300–420-second measured clip range. The module-end quiz stays separate; these checks do not award grades or mastery. Existing Module 1 plans and media without checkpoint metadata remain unchanged.

Codex-assisted ILD authoring is a separate new-draft route (`codex-ild-v2`). Codex is connected at authoring time through a one-course, expiring MCP bearer grant and saves a complete editable LMS package through a validated append-only revision API. Every module uses Problem Hook → Concept Explainer → Worked Example → Guided Practice → Scenario Lab, including two formative questions near the midpoint of each video. One Mini Project → creator-pass-rule Mastery Gate → Reflection follows the final module; Spaced Review is omitted. Course sizing is flexible by objective and time budget. The package traces instructional items to SME source blocks and cited research, while source links remain unverified until human review. Exact-revision review is a distinct final author approval; no publishing path is provided. Narration may be rendered after script edits with local Kokoro and fingerprint-based clip reuse. The shared demo identity, process-bound audio jobs and local media storage remain limitations. Direct LMS generation requires a durable background worker; plugin availability is not a production runtime dependency. See [Codex-assisted ILD course creation](codex-ild-course-creator.md) and [content creator workflow](content-creator.md).
